# GPU queue and resource safety

`gods_mlops.jobs.queue.JobQueue` owns the durable submission contract. `submit(dataset_version, model_kind, config_version, rerun=False)` accepts only a published, currently training-ready dataset whose target is compatible with DETR or CLIP. It reads Task 6's mutable readiness overlay at submission and again immediately before admission. A source tombstone blocks retraining; evaluation ineligibility by itself does not. Qwen is fixed caption inference and cannot be submitted as a training target.

Automatic submissions deduplicate on phase, typed input kind and ID, immutable input hash, model kind, target phase, and config hash. Explicit reruns always get a new job ID. Preparation uses `AnnotationPreparationBatch` values made from received frame and ready crop references. The source registry re-reads each ID, byte hash, crop revision, object key, and size before queueing. These pre-publication refs remain `input_kind=annotation_batch` with no `dataset_version`; they do not create a training manifest. Model VRAM probes use a distinct `probe_input` identity and the same queue.

Resource profiles are immutable, versioned records. A profile starts as a candidate. A successful probe persists the input/config hashes, measured peak allocation and reservation, exit status, checkpoint identity, and verifier details before promoting the profile to `measured`. DETR and CLIP training probes require at least three optimizer steps and a verified save/reload/resume. The Task 8 adapter supplies its model-specific proof; for CLIP that proof must also establish the approved explicit-negative and nonzero-update contract. DETR, CLIP, and fixed Qwen inference probes can produce separate preparation profiles. Only measured profiles can admit preparation/training work; a candidate waits for measurement without holding a GPU lease.

`GpuAdmission.admit(job_id, observation)` consumes a recent observation from the configured Ubuntu host, verifies its machine fingerprint, A6000 model and UUID, and configured filesystem identity, then persists it. A complete process listing is required. Seven distinct five-second samples must show 30 seconds without a GPU compute process; a gap over ten seconds or a repeated observation ID resets or blocks the window. Admission makes one more SSH observation immediately before acquiring the lease, so a process that appears after the idle series resets the decision. Storage must show at least 1 TiB available on the configured Ubuntu filesystem, and free VRAM must cover the versioned profile plus 4 GiB safety. The scheduler never derives model capacity from current free VRAM and never falls back to vis-lab's GPU.

The PostgreSQL lease is a single A6000 slot with expiry, UUID token, and increasing fence generation. Expiry does not release an owner. The monitor compares PID plus kernel start time and requires complete process and CUDA listings to prove the owned PID has exited and its GPU allocation is gone. A reused PID still appearing in the CUDA list remains busy. If another process starts while a job runs, the queue asks that job's own worker to checkpoint and exit. It does not signal or stop unrelated processes. A waiting job holds no GPU lease.

`FileCheckpointStore` writes immutable hash-keyed payload bytes, fsyncs and renames them, then publishes verified metadata as the commit marker. A checkpoint identity contains job, phase, input kind/ID/hash, model, dataset version when applicable, and config version/hash. Orphan/partial payloads are ignored; mismatched input/config identities cannot resume. The queue publishes the metadata marker only while the current lease token is locked. A stale token cannot update the job checkpoint. Profiles reserve bounded space for two checkpoint versions during atomic replacement and leave a separate result/model allocation inside the shared `ingestion_storage_usage` 1 TiB ledger. Capacity waits stay distinct from failures.

Communication failures schedule up to three retry waits of 10, 30, and 90 seconds. A fourth failure is terminal. External GPU use is a resource wait, not a communication or OOM retry. OOM fallback is limited to two new job IDs using already measured, strictly lower-memory profiles named by the original config. Each child pins its own config identity and cannot reuse a checkpoint from the parent config. An unmeasured, equal/larger, or absent alternative fails terminally, including a batch-one profile with no validated smaller candidate.

The `gods-mlops-resource-observer` Deployment is pinned to the non-GPU `vis-lab` node and requests no GPU. The observer and receiver read the same configured Ubuntu node ID, machine fingerprint, A6000 UUID, filesystem identity, and storage path. The observer refuses to start without those pins and writes only observations that match them; the receiver remains closed if its corresponding pins are missing. The observer uses the existing SSH identity and a Kubernetes Secret containing the private key plus the pinned `known_hosts` entry; the code enforces `BatchMode` and strict host-key checking. It reads the configured Ubuntu A6000 UUID and filesystem, then stores the latest observation in the shared PostgreSQL database every five seconds. The ingestion API reads that same row before reserving a new candidate. Missing, stale, failed, wrong-node/host/device/filesystem/path, or low-space observations pause new IDs with a retryable 503 reason. An already-received same-ID/same-hash request returns its durable receipt before the gate so lost-ack retries continue to work. Until deployment creates `/data/jayn2u/gods-mlops` and starts the observer, the production gate remains closed.
